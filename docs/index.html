🛡️ Sentinel 3.0 – Complete Setup Guide

GitHub Pages dashboard + Supabase (Auth, Postgres, Edge Functions) + Windows agent. No Railway. No webcam.

🪟 Windows 10/11🐍 Python 3.10+⚡ Supabase🐙 GitHub Pages⏱ ~60 minutes
OVERVIEW

What You'll Build

☁️ Cloud

GitHub Pages serves the static dashboard. Supabase Auth signs admins in (password + TOTP). Supabase Postgres stores everything behind Row Level Security. Edge Functions are the only code that writes data. A daily GitHub Action keeps the project active.

🖥️ Windows agent

A Python Windows Service that watches Windows logins, USB storage, protected folders, applications, Defender/firewall and its own integrity. It buffers events in an encrypted local queue and uploads them over HTTPS to Edge Functions only.

ℹ️

Order matters: Supabase → GitHub → first admin → Windows agent. You need the Supabase project URL, the publishable key and an enrollment token before the agent can register.

BEFORE YOU START

What You Need

Accounts (free tiers work)

  • GitHub – hosts code, Pages and the keep-alive workflow. Note: GitHub Pages on a free personal account requires a public repository. The repo contains no secrets (keys live in Supabase/GitHub secrets), but the source is visible. A paid GitHub plan allows Pages from a private repo.
  • Supabase – supabase.com

Software

  • Node.js 18+ (for the Supabase CLI) and Git on your admin PC
  • Python 3.10+ on each laptop to monitor (or a built SentinelAgent.exe)
  • An Administrator command prompt on each laptop

PHASE 1

Step 1 — Create the Supabase project

1A

Create it

  1. supabase.com → New project. Pick the region closest to you.
  2. Set a strong database password and store it in a password manager (you will not need it day-to-day).
  3. When it finishes provisioning open Project Settings → General and copy the Project ID (the REF used below).
  4. Open Project Settings → API Keys and copy the Project URL and the publishable key (older projects: anon key). You will put these two public values on GitHub.
🔒

Never copy the secret / service_role key anywhere except Supabase's own secrets. Edge Functions already receive it automatically.

PHASE 1

Step 2 — Install the CLI and link the project

2A

Get the code and link

git clone https://github.com/YOUR-USER/sentinel.git
cd sentinel
npm install -g supabase        # or: scoop install supabase
supabase login
supabase link --project-ref REF
PHASE 1

Step 3 — Apply the database migration (tables + RLS)

3A

Push

supabase db push

This creates 17 tables, indexes, the append-only triggers, the admin/MFA helper functions and Row Level Security. RLS is enabled and forced on every table; anon has no privileges at all; authenticated gets read-only access and only if is_admin() is true; device_credentials and enrollment-token hashes are unreachable from the browser.

3B

Verify (optional but recommended)

In SQL Editor run: select relname, relrowsecurity, relforcerowsecurity from pg_class c join pg_namespace n on n.oid=c.relnamespace where n.nspname='public' and c.relkind='r'; — every row must show true | true.

PHASE 1

Step 4 — Authentication settings

4A

Harden Auth

Open Authentication in the dashboard and set:

  • Sign In / Providers → Allow new users to sign up: OFF (the first admin is created by the bootstrap function, which is unaffected)
  • Email provider → Minimum password length: 12; require upper/lower/digits/symbols
  • Multi-Factor → TOTP: enabled
  • Sessions: JWT expiry 3600 s, refresh-token rotation on
  • Rate limits: keep sign-in limits at the defaults or stricter (brute-force protection)
  • URL Configuration → Site URL: your Pages URL (set in Step 7)

These values are also in supabase/config.toml; you can apply them with supabase config push instead of clicking.

PHASE 1

Step 5 — Secrets and Edge Functions

5A

Generate three random secrets

python -c "import secrets;print(secrets.token_urlsafe(48))"   # run 3 times: pepper, health-check, bootstrap
5B

Store them in Supabase (not in Git)

supabase secrets set DEVICE_SECRET_PEPPER=<secret 1> HEALTHCHECK_SECRET=<secret 2> BOOTSTRAP_SECRET=<secret 3> ALLOWED_ORIGIN=https://YOUR-USER.github.io
🔒

Back up DEVICE_SECRET_PEPPER. If it is ever lost or changed, every device secret and token stops verifying and all laptops must be re-enrolled. ALLOWED_ORIGIN is the origin only (no path, no trailing slash).

5C

Deploy all functions

supabase functions deploy
# expect 8 functions: admin-api admin-bootstrap device-command-result device-events device-register device-rotate device-sync health-check

The functions verify their own credentials (admin JWT, device secret or shared secret), so verify_jwt = false is set in config.toml for each.

PHASE 2

Step 7 — GitHub Pages and the public config

7A

Repository variables (public values)

Settings → Secrets and variables → Actions → Variables → New repository variable:

SUPABASE_URLhttps://REF.supabase.co
SUPABASE_PUBLISHABLE_KEYthe publishable / anon key

The deploy workflow refuses to run if the key looks like a secret key.

7B

Enable Pages from Actions

  1. Settings → Pages → Build and deployment → Source: GitHub Actions
  2. Actions → Deploy dashboard to GitHub Pages → Run workflow
  3. When green, open https://YOUR-USER.github.io/sentinel/
  4. Back in Supabase set Site URL to that address, and confirm ALLOWED_ORIGIN equals https://YOUR-USER.github.io.
PHASE 2

Step 8 — Keep-alive workflow

8A

Repository secrets

SUPABASE_FUNCTIONS_URLhttps://REF.supabase.co/functions/v1
HEALTHCHECK_SECRETexactly the value from Step 5B (secret 2)
8B

Test it now

Actions → Supabase keep-alive → Run workflow. Expect attempt 1: HTTP 200 and Keep-alive OK. It then runs daily at 03:00 UTC, retries 5× with back-off on network errors, does not retry a 401, and opens a GitHub issue if it fails. The dashboard Overview also shows a yellow banner if no successful check was recorded in 36 hours.

⚠️

This creates real daily database activity, but Supabase decides what counts as activity. It is not a guarantee against pausing. If uninterrupted monitoring is essential, use a paid Supabase plan. GitHub also disables scheduled workflows after 60 days without repository activity — a push or manual run re-enables it.

PHASE 3

Step 9 — Create the first administrator

9A

Bootstrap (works once, only while no admin exists)

curl -X POST https://REF.supabase.co/functions/v1/admin-bootstrap ^
  -H "x-bootstrap-secret: <secret 3>" -H "Content-Type: application/json" ^
  -d "{\"email\":\"you@example.com\",\"password\":\"a-long-unique-passphrase\"}"

Success: {"ok":true,...}. The password (12+ chars) is handed straight to Supabase Auth; Sentinel never stores it. The account gets the owner role in admin_profiles — a role no ordinary user can assign, because there is no browser-writable path to that table.

9B

First login

Open the dashboard, sign in with that email and password. You land on Overview.

PHASE 3

Step 10 — MFA and lock-down

10A

Enable TOTP

Settings → Two-factor authentication → Set up authenticator app, scan the QR code, enter the 6-digit code. From now on the database itself rejects any session that has not passed MFA (RLS function mfa_satisfied), and the Edge Functions do the same check.

10B

Remove the bootstrap secret and confirm sign-ups are off

supabase secrets unset BOOTSTRAP_SECRET

Test: calling Supabase's /auth/v1/signup with a new email must return "Signups not allowed". If it creates a user, turn off sign-ups (Step 4A). Even then, that user has no admin_profiles row and sees nothing.

Phases 1–3 done. The cloud side is complete.

PHASE 4

Step 11 — Prepare the Windows laptop

11A

Install Python and dependencies

  1. Install Python 3.10+ from python.org with Add Python to PATH ticked.
  2. Copy the agent folder to the laptop (e.g. C:\Sentinel\agent). Keep it somewhere only administrators can write.
# Administrator Command Prompt
cd C:\Sentinel\agent
pip install -r requirements.txt
python -m pywin32_postinstall -install
11B

Turn on Windows auditing (needed for login events)

Windows only writes login/account events if auditing is enabled. Run once as Administrator:

auditpol /set /subcategory:"Logon" /success:enable /failure:enable
auditpol /set /subcategory:"Logoff" /success:enable
auditpol /set /subcategory:"Account Lockout" /failure:enable
auditpol /set /subcategory:"User Account Management" /success:enable /failure:enable
auditpol /set /subcategory:"Security Group Management" /success:enable /failure:enable
auditpol /set /subcategory:"Audit Policy Change" /success:enable

Event IDs used: 4624 logon, 4625 failed logon, 4634/4647 logoff, 4720 user created, 4726 user deleted, 4732/4733 local group member added/removed, 4740 lockout, 4719 audit policy change, 1102 audit log cleared. The agent starts reading from now; it never replays old history.

PHASE 4

Step 12 — Register the laptop

12A

Create a one-time enrollment token

Dashboard → Settings → Enroll a new laptop → label it, choose how long it is valid, Create one-time token, copy it (shown once). It works for exactly one registration.

12B

Register (Administrator prompt on the laptop)

python run_agent.py register
Functions URLhttps://REF.supabase.co/functions/v1
Device namee.g. Johns-Laptop
One-time enrollment tokenpaste (hidden)

The server returns a unique device ID and secret once. The secret is encrypted with Windows DPAPI into C:\ProgramData\Sentinel\secret.bin and the folder is restricted to SYSTEM and Administrators. It is never printed or written to a plaintext JSON file.

PHASE 4

Step 13 — Install and start the service

13A 
python run_agent.py install
python run_agent.py start
sc query SentinelAgent          # STATE : 4 RUNNING
python run_agent.py status        # checks service, config and credential store
type C:\ProgramData\Sentinel\logs\sentinel.log

Install sets delayed automatic start and a recovery policy: restart after 1, 2 and 5 minutes, then stop (so a broken agent can never loop forever). Every restart is reported as an unclean_shutdown event, and 4+ starts in 10 minutes raises a critical service_crash_loop. If the config or credentials are missing/corrupt the service stays up but idle, logs why, and the dashboard shows the laptop go silent.

Within ~30 seconds the laptop shows Online on the dashboard. Other commands: stop, restart, remove.

⚠️

Edits to config.json take effect after a service restart. Changing server_url, device_id or service_name while running is reported as config_tampered (critical).

PHASE 4

Step 15 — Publish the trusted release hashes

15A

Why

Hashes stored beside the agent can be edited together with the agent. Sentinel therefore compares what each laptop reports with a manifest you published to the server, and with first-seen baselines of its config and service registration.

# on your trusted build machine, from the repo root
python tools/make_manifest.py --source agent        # running from source
python tools/make_manifest.py agent/dist/SentinelAgent.exe   # frozen build

Dashboard → Settings → Agent releases (owner only): version 3.0.0, paste the JSON, tick Mark as latest, Publish. A laptop whose files differ gets integrity: mismatch and a critical alert. After a legitimate upgrade publish the new manifest and use Accept current as baseline on the device's Agent Health tab.

PHASE 4 — OPTIONAL

Step 16 — Sysmon for deeper process visibility

16A
  1. Download Sysmon from Microsoft Sysinternals.
  2. Install with the low-volume config shipped in docs\sysmon-minimal.xml: sysmon64.exe -accepteula -i docs\sysmon-minimal.xml
  3. Edit C:\ProgramData\Sentinel\config.json: "sysmon_enabled": true, then python run_agent.py restart.

The shipped config only logs process creation for a short list of risky tools and encoded/download PowerShell, to keep CPU and disk use negligible. The agent reads only EventID 1 by default (sysmon_event_ids) and raises an event only when a process matches the watch-list. Check Sysmon's own log size in Event Viewer and keep it small.

PHASE 5

Step 17 — Using the dashboard

Overview & devices

Overview shows registered/online/offline counts, critical and high alert counts, outdated agents, integrity problems, recent incidents and recent administrator actions. Click a laptop for its own dashboard with tabs: Overview, Security Events, Windows Logins, File & Folder, Applications, USB, Agent Health, Commands, Settings. Every tab shows only that device.

Device status words

  • Online – contacted within the offline threshold (120 s)
  • Unresponsive – quiet for 2–15 min
  • Offline – quiet > 15 min
  • Agent stopped – the agent reported a deliberate stop (service stop/shutdown)
  • Revoked – credentials revoked
  • Never connected – enrolled but no sync yet

Blocked apps and protected folders

Device → Settings: one executable per line (chrome.exe) and one full folder path per line. Blocked apps are only terminated while in Secure Mode. Protected-folder changes are logged in any mode (created/modified/deleted/renamed, path and time only — never file contents). Save; the laptop picks it up on its next sync (≤ 30 s by default).

Secure Mode and emergency commands

Device Overview → Emergency response. Commands: Secure Mode on/off, lock workstation, quick scan, health report, integrity check, refresh config, restrict apps (temporary), rotate credentials, network isolate/restore, mark compromised, revoke device. Sensitive ones ask for confirmation; revoke requires typing the device name.

A command is Pending (waiting for the laptop) → Delivered → Acknowledged → Executing → Completed/Failed. The dashboard only shows Completed after the laptop reports it, and Secure Mode in the dashboard only changes after the laptop confirms. Unclaimed commands expire (default 15 min).

Lock workstation disconnects the active console session (user returns to the sign-in screen) because a service cannot lock a desktop directly. Network isolate is off unless you set "allow_network_isolation": true in the laptop's config.json; it blocks outbound traffic except HTTPS to the IPs Supabase resolved to at that moment (may break if those change) and auto-restores after the timeout. Test it with the laptop physically with you first.

Logs, filters, export

Logs page (all devices) and each device tab support filters for device, date range, severity, category, source, event type, resolution status and text search, with 50-row pagination and CSV / JSON export. High/critical events can be marked resolved with a note (the original record is never altered). Security events are never deleted by Sentinel; only heartbeat samples can be pruned if the owner sets a retention period.

Severity

CriticalSentinel tampering, admin-group additions, audit log cleared, crash loops, rejected credentials
HighDefender/firewall/RDP settings weakened, user created/deleted, blocked app killed, lockouts
MediumFailed-login bursts, new USB device, RDP logon, protected-folder activity, config warnings

PHASE 6

Troubleshooting

🔴 Login says "Invalid email or password"

  • The message is intentionally generic. Confirm the account exists in Supabase → Authentication → Users.
  • Too many attempts → wait a few minutes (Auth rate limit).
  • "not an authorized Sentinel administrator": the user exists but has no admin_profiles row (run bootstrap, or it is not the bootstrapped email).

🔴 Dashboard shows empty tables / "permission denied" / RLS errors

  • You enrolled TOTP but signed in without the code in this browser session → sign out and in again; MFA-less sessions are denied on purpose.
  • permission denied for table … from the browser means you tried a write; writes only go through admin-api.
  • Never "fix" this by disabling RLS or granting anon access.

🔴 Edge Function errors

  • CORS error in the browser console: ALLOWED_ORIGIN is wrong (must be exactly https://USER.github.io). Re-run supabase secrets set; no redeploy needed.
  • 500 internal_error: Supabase → Edge Functions → the function → Logs. A message about DEVICE_SECRET_PEPPER means that secret is missing or under 32 characters.
  • 404 / not found: run supabase functions deploy.
  • 401 unauthenticated / 403 mfa_required from admin-api: sign in again with the TOTP code.

🔴 GitHub Pages not deploying / blank page

  • Settings → Pages → Source must be GitHub Actions.
  • Workflow fails with "Set repository VARIABLES": add SUPABASE_URL and SUPABASE_PUBLISHABLE_KEY under Variables (not Secrets).
  • Page says "config.js is not configured": the workflow did not run after you added the variables — run it again.
  • Free accounts need a public repo for Pages.

🔴 Keep-alive workflow fails or never runs

  • Missing repository secrets → add SUPABASE_FUNCTIONS_URL and HEALTHCHECK_SECRET as Secrets.
  • 401 → the GitHub secret differs from the Supabase one. Re-set both with the same value.
  • Schedules pause after 60 days of repo inactivity and may start late (GitHub runs them best-effort). Run it manually to re-arm.
  • If the Supabase project is paused: Supabase dashboard → Restore project.

🔴 Registration fails

  • invalid_enrollment_token: token already used, expired or mistyped. Create a new one.
  • rate_limited: wait a minute.
  • Could not reach the server: check the Functions URL ends with /functions/v1 and begins with https://.

🔴 Device shows Offline / no heartbeats

  • sc query SentinelAgent → must be RUNNING; else read C:\ProgramData\Sentinel\logs\sentinel.log and the Windows Event Viewer → Application.
  • python run_agent.py status shows missing/corrupt config or credentials. If the secret store is damaged, revoke the device in the dashboard and enroll it again with a new token.
  • Firewall/proxy blocking outbound HTTPS to *.supabase.co.
  • Laptop clock wrong by more than a few minutes can distort timestamps (the server stores UTC).

🔴 Device authentication failures (log: "server rejected device credentials")

  • device_auth_failures in SQL editor lists reasons: bad_secret, unknown_device, malformed.
  • Pepper changed since enrollment → all devices fail; restore the original DEVICE_SECRET_PEPPER.
  • Credentials rotated while the laptop was off before it stored the new secret (rare) → revoke and re-enroll.
  • Revoked devices receive 403 revoked and show Revoked.

🔴 Offline events not syncing

  • Events wait in C:\ProgramData\Sentinel\events.db and keep their original timestamps. They are deleted locally only after the server acknowledges them, and duplicates are impossible (per-device dedup id).
  • Agent Health shows buffer usage; an alert is raised at 80% and 95%. When full, only low/medium events are dropped (counted and reported); high/critical are never dropped.
  • A corrupt buffer is quarantined as events.db.corrupt-<time> and a high event is raised.

🔴 No Windows login events

  • Run Step 11B (auditing). The service must run as LocalSystem (the default) to read the Security log.
  • An eventlog_unreadable event in the logs says what failed.

🔴 Service install: "Access denied" / starts then stops

  • Use an Administrator prompt. Register before installing.
  • pywin32_postinstall not run → python -m pywin32_postinstall -install.
  • Service stays idle with "cannot start": fix the reported config/credential problem and restart.
MIGRATION

Moving from the old Railway version, and rolling back

What this package does and does not migrate

Sentinel 3.0 was built as a fresh installation. The old FastAPI/Railway source code and data were not available to the build, so no data is imported and old agents are not compatible (new endpoints, new credential format). Every laptop must be re-enrolled with a new one-time token.

  1. Leave the Railway service running and untouched while you set up and verify Sentinel 3.0 on one laptop.
  2. Export what you need from the old dashboard/database (e.g. pg_dump from Railway) and keep it as an archive. Old photos are not carried over.
  3. On each laptop: stop and remove the old service (python service.py stop, python service.py remove), delete the old agent/data folder (it holds the old secret), install 3.0 (Steps 11–13).
  4. When all laptops report to Supabase, delete the Railway project and its PostgreSQL plugin.

Rollback: python run_agent.py stop, python run_agent.py remove, reinstall the old agent folder and run its setup wizard against the still-running Railway server. Nothing in Railway is modified by 3.0. Database changes in Supabase are fully contained in one migration; deleting the Supabase project removes it.

HONESTY

Security limitations

  • Not tamper-proof. A local administrator can stop the service, kill the process or edit files. Sentinel's goal is detection, evidence and alerting: a deliberate stop is reported as agent stopped; a kill or crash is reported as unclean shutdown on next start and as a silence (Unresponsive/Offline, plus a device_silent alert after 1 hour). If an attacker never lets the laptop reconnect, you only see the silence.
  • DPAPI machine scope protects the secret from other users and offline disk theft, but any code running as SYSTEM/Administrator on that laptop can decrypt it.
  • Server-side integrity is only as good as your manifest. A fully compromised agent that forges reports using the stolen device secret can lie. Revoke and rebuild such a device.
  • Log immutability: ordinary roles cannot edit or delete security events (RLS + triggers), and daily hash-chain checkpoints make silent edits detectable. Anyone with database-owner access (including you, in the Supabase dashboard) can still disable triggers — that is a privileged trust boundary, not absolute immutability.
  • No process attribution for file events (Windows does not reliably report which process changed a file); only path, operation and time are recorded.
  • Auto-update is intentionally not implemented because update authenticity cannot be verified without code signing. The dashboard shows installed vs latest version; update manually.
  • Rate limiting in Edge Functions is per function instance (best effort). Auth brute-force protection relies on Supabase Auth's own limits.
  • Free-tier Supabase projects can pause and have storage limits; plan retention/export accordingly. Heartbeats are sampled every 5 minutes to keep volume low.
